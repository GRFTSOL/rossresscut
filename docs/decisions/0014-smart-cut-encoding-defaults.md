# ADR-0014：Smart cut 的编码后端与默认参数

## 状态

Accepted

## 背景

`OQ-22` 询问是否接入硬件编码器（NVENC / VAAPI / VideoToolbox）。
Smart cut 只重编码请求起点到下一个关键帧、以及终点前最后一个关键帧到终点；
当片段完全位于两个关键帧之间时整段重编码。编码量取决于 GOP 长度，不是固定几帧。

实测（FFmpeg 9.0.2，本机）：

| 场景 | 重编码量 | 耗时 |
| --- | --- | --- |
| 4K60 HEVC，片段完全落在一个 5s GOP 内 | 2s | 18.6s（默认 `medium`） |
| 4K60 HEVC，头尾各约 4s | 8s | 64.6s（默认 `medium`） |
| 1080p60 HEVC，片段完全落在一个 5s GOP 内 | 2s | 8.4s（默认 `medium`） |

因此 CPU 编码在功能上可用，但 4K 长 GOP 场景仍会明显占用 CPU。

## 决策

### D1：当前保持软件编码，不接硬件编码器

不实现 NVENC / VAAPI / VideoToolbox。理由：

- 硬件编码器的可用性、质量和输出差异依赖本机 GPU 与驱动；
- 项目要求导出结果可复现，且不为假想需求引入设备探测与回退分支；
- 当前 smart cut 的重编码片段通常只有数秒，软件编码可以接受。

`OQ-22` 的解除条件由本 ADR 记录：硬件编码的使用边界与降级语义暂不引入。
如果以后出现真实的 4K 长片段性能需求，再单独评估“可选硬件编码 + 明确降级”。

### D2：固定性价比 preset

使用真实素材与 VMAF 选择。测试片段均为 2s、目标码率 = 源视频平均码率 × 1.5；
VMAF 使用默认 `vmaf_v0.6.1` 模型，并先按帧序号对齐。

素材：

- 1080p60 HEVC `戴上耳机别眨眼，带你领略中华武术的魅力.mp4`（3.10 Mbps）
- 1080p60 HEVC `【硬核】干掉光猫！…mp4`（0.45 Mbps，低码率复核）
- 4K60 HEVC `“监控”四位同事30天…mp4`（2.07 Mbps）

x264（1080p60，4.65 Mbps）：

| preset | 耗时 | VMAF |
| --- | --- | --- |
| superfast | 1.54s | 91.11 |
| veryfast | 1.90s | 93.29 |
| **faster** | **2.77s** | **94.50** |
| fast | 3.36s | 94.49 |
| medium | 3.97s | 94.78 |

低码率复核：veryfast 75.81，faster 79.43。
`faster` 是最后一个有明显收益的档位；再往后 VMAF 基本不再上升。

x265：

| 素材 | preset | 耗时 | VMAF |
| --- | --- | --- | --- |
| 4K60 | superfast | 10.30s | 91.43 |
| 4K60 | **veryfast** | **13.86s** | **92.33** |
| 4K60 | faster | 14.07s | 92.31 |
| 4K60 | fast | 19.53s | 92.28 |
| 1080p60 | superfast | 5.24s | 94.61 |
| 1080p60 | **veryfast** | **7.29s** | **95.23** |
| 1080p60 | faster | 7.52s | 95.26 |

`veryfast` 之后 VMAF 不再提升，`faster` / `fast` 只增加耗时。

SVT-AV1（1080p60，4.65 Mbps）：

| preset | 耗时 | VMAF |
| --- | --- | --- |
| 10 | 2.65s | 93.51 |
| **9** | **3.13s** | **95.27** |
| 8 | 4.58s | 95.52 |
| 7 | 6.30s | 95.73 |
| 6 | 10.39s | 96.66 |

10 → 9 是最大的质量跃升；9 之后每提升不到 0.5 VMAF 都要多花 50% 以上时间。

最终选择：

| 编码器 | preset |
| --- | --- |
| `libx264` | `faster` |
| `libx265` | `veryfast` |
| `libsvtav1` | `9` |

其他编码器（`libvpx-vp9`、`prores_ks` 等）保持 FFmpeg 默认参数。
preset 只在 smart cut 重编码时使用，通过 `-preset` 显式传递。

VMAF 对齐说明：直接用 `setpts=PTS-STARTPTS` 会受到首帧时间戳差异影响，
把无损编码也压到 85 左右。测试时必须按帧序号对齐
（例如 `settb=1/1000,setpts=N`）；对齐后同一素材的无损编码 VMAF 为 98.99。

### D3：码率默认按需编码片段的源平均码率 × 1.5

- 规划阶段在 worker 线程逐段探测需要重编码片段的视频包大小，
  计算该片段的源平均码率。
- 目标码率 = 该片段源平均码率 × 1.5；探测失败时回退到整条视频流平均码率 × 1.5。
- 设置中可填写固定码率（kbps）；`0` 表示自动。手动值直接使用，不再乘 1.5。
- 码率只影响重编码片段，不影响无损中段。

## 后果

- 不增加 GPU 依赖；导出仍可在无硬件编码器的机器上工作。
- `libx264` / `libx265` / `libsvtav1` 的短片段编码速度明显改善。
- 4K 长 GOP 仍可能需要数十秒；UI 必须继续显示进度与取消。
- 每个需要编码的片段多一次 FFprobe 包大小探测，发生在规划线程，
  不阻塞 UI。
- 硬件编码仍是未来的可选方向，需要新的 ADR。
