# 0005 硬件解码默认启用

- 状态：预览实现部分已被 `0009-preview-decode-zero-copy.md` 取代；「默认启用硬件解码、回退必须可见」的原则继续有效
- 日期：2026-10-24
- 阶段：Phase 2 修订
- 取代：`0004-audio-clock-and-desktop-integration.md` §2

## 背景

`0004` 曾根据本机 wall-clock 测量决定默认关闭硬件解码，并记录“VAAPI 更慢”的结论。项目负责人指出该测试机同时运行编辑器，CPU 被严重占用，测量结果不能代表一般硬件；并明确要求默认启用硬件解码：

- Linux：VAAPI
- Windows：D3D11VA
- macOS：由实现选择

因此需要重新记录决策，且不能再把本机计时作为关闭硬件解码的理由。

## 已知约束

- 禁止 `unsafe` 与 FFI；只能通过外部 FFmpeg 进程使用硬件解码。
- 预览帧最终要缩放为 RGB24 并上传给 egui，当前不是 GPU 零拷贝管线。
- 硬件设备与 codec 支持因机器而异，必须有软件回退路径。
- 媒体处理（导出、裁切、合并）与预览是不同职责；本决策只影响预览。

## 候选方案

### 方案 A：固定软件解码

优点：

- 行为最一致，不依赖 GPU 设备。
- 不增加设备检测与回退逻辑。

缺点：

- 与项目负责人的产品要求冲突。
- 现代 GPU 上 CPU 占用更高。

### 方案 B：按平台默认硬件解码，设备不可用时回退软件

优点：

- 符合产品要求。
- 高分辨率素材可显著降低 CPU 占用。
- 单一命令构造点即可覆盖三个桌面平台。

缺点：

- FFmpeg 对不支持的 codec 可能内部回退，当前无法从进程输出可靠区分实际解码器。
- 帧仍需下载到 CPU，收益受预览管线限制。

### 方案 C：GPU 零拷贝预览管线

超出当前阶段范围，需要重构帧传输与纹理上传。

## 决策

选择：

> 方案 B。

具体参数：

```text
Linux:   -hwaccel vaapi -hwaccel_device /dev/dri/renderD128
Windows: -hwaccel d3d11va
macOS:   -hwaccel videotoolbox
```

- Linux 启动时检查 render node；不存在时不添加硬件参数，并记录 warning。
- 播放信息显示请求的后端；软件路径显示 `ffmpeg (software)`。
- 不为了绕过硬件解码问题而默认关闭它；回退必须可见。

## 决策理由

1. 项目负责人明确要求启用，且本机测量环境不可信。
2. 硬件解码降低 CPU 占用，符合低资源占用的产品目标。
3. 设备缺失时回退软件，不会让无 GPU 的机器无法播放。

## 后果

### 正面

- 高分辨率 HEVC 等素材默认走 GPU 解码。
- 解码后端集中在 `PreviewVideoConfig`，命令构造可单元测试。

### 负面

- 播放信息中的 Decoder 是请求值，不保证 FFmpeg 实际使用了该后端。
- 硬件解码的帧仍要下载到 CPU，不是零拷贝。

### 后续影响

- 若需要准确报告实际解码器，需要解析 FFmpeg stderr 或使用 `-loglevel verbose`，属于后续独立改动。
- Segment、导出与无损语义不得依赖预览解码路径。

## 未解决问题

- 非 `/dev/dri/renderD128` 的多 GPU 机器如何选择设备。
- 是否引入 GPU 零拷贝预览。
