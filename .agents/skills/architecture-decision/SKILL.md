# 架构与产品决策访谈

本 Skill 用于本项目中需要用户做出明确取舍的架构决策和产品决策。

核心原则：

> **Agent 调查事实，Agent 分析方案，用户决定取舍，项目文档记录结果。**

不要把能够通过阅读代码、官方文档、实际测试或最小实验确定的问题抛给用户。

---

## 一、什么时候使用

在以下情况下使用本 Skill：

- 存在多个合理的架构方案。
- 选择会影响后续多个 Phase。
- 选择会影响核心数据模型。
- 选择会增加或减少长期依赖。
- 选择会影响跨平台行为。
- 选择会改变用户可见行为。
- 选择会影响媒体处理正确性。
- 选择会影响无损编辑语义。
- 选择一旦确定，后续修改成本较高。
- `AGENTS.md`、现有文档和代码无法直接确定正确方案。

典型例子：

- 视频预览后端选择。
- 播放与 seek 的实现策略。
- 时间戳内部表示。
- VFR 的处理策略。
- 非关键帧切点的行为。
- stream copy 与 smart cut 的产品行为。
- 多片段导出的组织方式。
- 音视频流选择规则。
- FFmpeg 进程模型。
- 是否引入某个新的 Rust crate。
- 项目文件格式。
- 跨平台 FFmpeg 分发方式。

---

## 二、什么时候不要使用

以下情况不要启动决策访谈。

### 1. 可以通过代码确认

例如：

- 某个类型在哪里定义。
- 某个函数目前如何调用。
- 当前项目有哪些依赖。
- 某个模块已经提供什么能力。

先阅读代码。

### 2. 可以通过官方文档确认

例如：

- Rust API 的行为。
- egui / eframe API。
- FFmpeg 参数含义。
- crate 是否支持某个平台。

先查官方文档。

### 3. 可以通过实验确认

例如：

- 某个 FFmpeg 参数是否真的有效。
- 某种容器是否可以 stream copy。
- 某种 seek 行为是否准确。
- 某个播放器后端在当前平台是否可用。

先进行最小实验。

### 4. 只是实现细节

例如：

- 一个函数叫什么。
- 一个模块内部使用 `Vec` 还是其他标准数据结构。
- 一个错误类型如何组织。

如果不会影响项目级决策，不需要询问用户。

---

# 三、开始访谈前必须做的事情

不要一进入 Skill 就开始提问。

首先检查项目：

1. 阅读 `AGENTS.md`。
2. 阅读 `GOALS.md`。
3. 阅读 `PLANS.md`。
4. 阅读相关 `docs/`。
5. 检查当前代码。
6. 检查已有依赖。
7. 检查已有测试。
8. 检查已有 `docs/decisions/`。
9. 确认当前 Phase。
10. 判断问题究竟属于：
   - 技术事实；
   - 架构决策；
   - 产品决策；
   - 尚未明确的问题。

如果通过以上步骤已经可以得出结论，不要启动访谈。

---

# 四、先调查，再提问

对于每一个候选方案，Agent 应尽可能自己完成调查。

至少考虑：

- 当前代码是否支持。
- 对现有架构的影响。
- 新增依赖。
- 运行时依赖。
- 跨平台支持。
- 性能。
- 内存占用。
- 实现复杂度。
- 测试难度。
- 后续维护成本。
- 对后续 Phase 的影响。
- 是否违反 `AGENTS.md`。
- 是否与已有 ADR 冲突。

如果需要外部信息：

- 优先官方文档。
- 对 Rust crate 优先 crate 官方文档 / 仓库。
- 对 FFmpeg 优先 FFmpeg 官方文档。
- 对 egui / eframe 优先官方文档。
- 不要把未经验证的博客、论坛答案当成事实。

### 复杂媒体处理问题

遇到复杂媒体处理问题，优先调查成熟开源实现的实际行为，再设计本项目实现。

适用于：FFmpeg 参数、时间戳、stream copy、keyframe、smart cut、concat、音画同步、容器兼容性、metadata、字幕、chapter。

调查顺序：

1. 本项目已有代码 / ADR。
2. FFmpeg 官方文档。
3. LosslessCut 实现与 issue / commit。
4. 实验验证。
5. 设计本项目实现。

参考实现只用于理解行为与语义。LosslessCut 使用 GPL-2.0：不复制源代码，不把 TypeScript 逐行翻译成 Rust。

如果技术事实无法确定：

> 明确标记为“未知”，并通过最小实验验证。

不要把猜测包装成事实。

---

# 五、区分事实、推论和决策

在访谈过程中明确区分三类内容。

### 已知事实

能够由代码、文档或实验直接确认。

例如：

```text
当前项目使用 eframe。
当前项目没有视频解码 crate。
FFmpeg 通过外部进程调用。
```

### 推论

基于事实进行的技术分析。

例如：

```text
如果直接增加某播放器 crate，
项目依赖数量会增加，并可能引入额外运行时。
```

### 决策

必须由项目负责人选择的取舍。

例如：

```text
是否愿意增加一个依赖来换取成熟的预览能力？
```

只有第三类问题应该交给用户决定。

---

# 六、提问规则

## 1. 一次只问一个核心决策

不要一次发送十几个问题。

错误：

```text
你觉得预览用 mpv、GStreamer、FFmpeg、
哪个平台优先、是否支持硬解、
是否允许额外依赖、音频怎么处理、
seek 要多精确？
```

正确：

```text
先决定预览后端允许增加怎样的运行时依赖。
```

用户回答之后，再继续下一个受影响的决策。

---

## 2. 问题必须可以做决定

不要问：

```text
你怎么看？
```

应该问：

```text
当前有两个合理方案：

A. 使用已有外部播放器作为预览后端。
B. 在 Rust 应用内部管理解码流程。

我推荐 A，因为当前项目已经明确禁止过度增加架构复杂度。

你希望项目接受 A 的外部运行时依赖吗？
```

---

## 3. 给出 Agent 的推荐

如果 Agent 有足够证据，应明确给出推荐。

格式：

```text
### 当前问题

……

### 已知事实

- …
- …
- …

### 方案

A. …
B. …
C. …

### 推荐

推荐 B。

原因：

1. …
2. …
3. …

### 代价

- …
- …

### 需要你决定

……
```

不要假装所有方案完全等价。

---

## 4. 不要用问题逼用户替 Agent 做技术分析

禁止：

```text
你想用哪个 crate？
```

如果用户不需要知道全部技术细节，应先调查并提供：

```text
我检查了当前项目和候选方案。

方案 A：
- 优点……
- 缺点……

方案 B：
- 优点……
- 缺点……

基于项目现有约束，我推荐 A。

需要你决定的是：是否接受 A 带来的额外依赖。
```

---

# 七、优先询问高影响决策

如果存在多个决策，按照下面的优先级处理：

1. 会改变整体架构的决策。
2. 会锁定核心数据模型的决策。
3. 会影响后续多个 Phase 的决策。
4. 会增加长期依赖的决策。
5. 会影响跨平台能力的决策。
6. 会影响用户数据或媒体正确性的决策。
7. 一旦实现后修改成本很高的决策。
8. 普通产品行为。
9. 低影响实现细节。

高影响决策没有确定之前，不要继续实现依赖该决策的大量代码。

---

# 八、特别关注本项目的几个决策类别

## 1. 预览

涉及：

- 解码方式。
- 播放后端。
- seek。
- 音频。
- 视频帧获取。
- 硬件加速。
- 跨平台。
- egui 集成。

不要仅因为“能播放视频”就选择方案。

需要考虑：

```text
正确性
复杂度
依赖
性能
跨平台
维护成本
```

---

## 2. 时间系统

涉及：

- `Timestamp`
- `Duration`
- `TimeBase`
- PTS
- DTS
- VFR
- seek
- frame boundary

时间系统属于核心领域模型。

如果一个决定会改变 `docs/media-model.md` 或核心时间类型，优先进行决策访谈，并记录 ADR。

---

## 3. 无损编辑

涉及：

- stream copy。
- keyframe。
- 非关键帧切点。
- smart cut。
- 重新编码。
- 时间戳重写。
- 容器兼容性。

必须保持项目的核心原则：

> 不允许静默把无损操作降级为重新编码。

如果方案涉及降级，必须明确：

- 什么条件触发。
- 为什么触发。
- 用户是否知道。
- 如何向用户解释。
- 输出如何验证。

---

## 4. 依赖

新增 crate 时，不只问“能不能用”。

必须分析：

- 标准库能否解决。
- 当前依赖是否已经解决。
- crate 维护状态。
- license。
- 传递依赖。
- 编译成本。
- 二进制体积。
- runtime。
- 跨平台。
- 是否改变架构边界。

如果只是为了省少量代码而引入大型依赖，默认不推荐。

---

# 九、用户回答之后

用户做出决定后：

1. 用一句话确认最终决定。
2. 说明该决定将影响哪些部分。
3. 检查是否需要更新 ADR。
4. 不要继续询问已经确定的问题。
5. 不要擅自改变用户已经明确做出的决定。
6. 如果新事实与决定发生冲突，暂停实现并说明冲突。

不要因为后来发现了另一个“看起来更优”的方案，就默默推翻用户已经确认的决定。

---

# 十、创建 ADR

如果这是重大架构决策，应在 `docs/decisions/` 创建 ADR。

推荐格式：

```markdown
# ADR-XXXX：<决策名称>

## 状态

Accepted

## 背景

为什么需要做这个决定。

## 已知约束

- …
- …
- …

## 候选方案

### 方案 A

优点：

- …

缺点：

- …

### 方案 B

优点：

- …

缺点：

- …

## 决策

选择：

> 方案 B。

## 决策理由

1. …
2. …
3. …

## 后果

### 正面

- …

### 负面

- …

### 后续影响

- …

## 未解决问题

- …
```

ADR 只记录已经确定的决策。

不要把完整聊天记录复制进 ADR。

---

# 十一、决策完成后的实现

ADR 写入后，才进入实现阶段。

实现前重新检查：

```text
AGENTS.md
GOALS.md
PLANS.md
相关 architecture 文档
相关 ADR
当前代码
```

然后：

1. 制定最小实现方案。
2. 修改代码。
3. 添加测试。
4. 运行验证。
5. 更新必要文档。

不要因为完成了决策访谈，就自动扩大实现范围。

---

# 十二、如果用户拒绝做决定

如果用户说：

- “你决定。”
- “随便。”
- “按你觉得合理的来。”

Agent 可以自行决定，但必须：

1. 明确说明这是 Agent 的技术判断。
2. 给出选择理由。
3. 如果是重大架构决策，仍然创建 ADR。
4. 不把 Agent 的选择伪装成用户的产品决定。

例如：

```text
你将该选择交给我。

基于当前项目约束，我选择方案 B。

这是技术判断，不是用户产品偏好。

原因：
1. …
2. …
3. …
```

---

# 十三、不要过度访谈

这个 Skill 的目标是减少错误决策，不是制造会议。

以下情况应直接做：

```text
明显的实现细节
标准 Rust 写法
已有文档明确规定的行为
可以通过测试确定的问题
可以通过官方文档确定的问题
不会影响架构的局部修改
```

只有真正存在取舍时才进入访谈。

核心判断：

> **如果 Agent 可以自己查清楚，就不要问用户。**
>
> **如果最终必须有人承担取舍，就让用户做决定。**

---

# 十四、完成标准

一次决策访谈完成后，必须满足：

- [ ] 事实与推论已经区分。
- [ ] 候选方案已经明确。
- [ ] Agent 已给出推荐，除非不存在合理推荐。
- [ ] 用户明确做出选择，或明确将决定交给 Agent。
- [ ] 没有遗留关键的未决问题。
- [ ] 重大决策已经记录到 ADR。
- [ ] ADR 与当前代码和项目文档一致。
- [ ] 后续实现范围明确。
- [ ] 没有因为访谈而引入不必要的抽象或依赖。

完成决策后，不要继续讨论已经解决的问题。

---

# 十五、最终原则

本 Skill 遵循以下决策顺序：

```text
阅读项目
    ↓
确认当前 Phase
    ↓
发现决策点
    ↓
调查事实
    ↓
验证未知问题
    ↓
列出候选方案
    ↓
给出推荐
    ↓
询问用户真正需要决定的取舍
    ↓
记录决定
    ↓
写 ADR
    ↓
实现
    ↓
测试
```

不要反过来：

```text
先问用户
    ↓
根据用户回答寻找事实
    ↓
临时设计架构
    ↓
写代码
```

**用户负责方向和取舍，Agent 负责调查、分析、实现和验证。**
